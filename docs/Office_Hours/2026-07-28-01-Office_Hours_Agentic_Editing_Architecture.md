> The founder arrived with a complete end-to-end architecture and the empirical finding that motivated it. The session pressure-tested it, the founder corrected two of the three objections, and the risk was relocated from where the partner initially placed it to where it actually sits: the productionalize step. This doc records the architecture, the premise it breaks in a prior session, and the open problems. The decision it produced is `pivots/2026-07-28-01-agentic-editing-all-in.md`.

## Problem statement

The 2026-07-27 pivot committed to a [[Concepts/Product/Mechanisms/Full_Visual_Redesign|full visual redesign]] with a two-part mechanism: assets are data so a pipeline generates them, layout is code so an agent writes it. It left the layout half almost entirely unspecified and named its hardest problem openly — *"layout has no deterministic accept condition the way colour has WCAG and OKLCH."*

This session answers: **what is the actual architecture of the layout half, and where does the risk really live?**

---

## The finding that motivated it

The founder tested **preset enums for structure** and found they don't work, for a reason that generalizes:

> *"I realized it's always going to be bounded by the design language originally. Every app has its own tokenized stuff and if it sticks to it it'll cease to be truly unique. And classification is also very rigid."*

This is the first piece of empirical evidence produced in this project. It was generated by building, not by reasoning, and it says something the founder did not want to hear: a bounded, classified, enum-driven structural system reproduces the platform's original design language no matter how many options it exposes. Structural presets are a reskin with more steps.

The founder's framing of the consequence:

> *"This is kinda like an OpenClaw moment — the more free you make the agent the better results you can get, but of course you have to be careful about the guardrails always."*

That reframes the entire layout half from *classification* to *free agency under invariants*.

## What this session breaks

> [!warning] Premise shake — 2026-05-25 Live Preview Rendering Architecture
> That session locked: *"The customization the product sells is token/asset-level — palette, typography, iconography, illustration, motion presets, copy register, logo — **not layout or structural redesign**."*
>
> The 2026-07-27 pivot to full visual redesign killed that premise, and nothing went back to check what depended on it. A great deal did. That session's entire architectural conclusion — Mechanism 0, compile the real app to web and push config over `postMessage` — was correct *for a product that never touches layout*. It is not sufficient for one that does.
>

That fact is repurposed below as the production-side validation oracle. Its original use (preview fidelity) is superseded; its underlying claim is load-bearing again for a different reason.

## The architecture

```
Platform grants READ access to their white-labeled codebase
   their trunk is never written to, at any point in this flow
        ↓
Tokenization agent → produces the SHARED TOKENIZED FORK (Recompose's base)
   forward-deployed for MVP; this is critical
   tokenizes every asset (images, colour, type) into slot references;
   does NOT mock anything — mocking belongs to the mirror
        ↓
Tokenization reviewed (by us; steerable by them if they want to be involved)
        ↓
Migration agent builds a JSX VISUAL MIRROR of the codebase
   mockware only — no features, no logic, no API calls, no state
   cached; regenerated only on merge to the platform's main
        ↓
Customer prompts for a design
        ↓
ThemeTree runs — assets, colours, icons, typography, copy
        ↓
Design agent works on the cached JSX with full freedom
   constrained only by: nothing added, nothing removed
        ↓
Design validator (loops with the design agent until accepted)
   validates against SCREENSHOTS
        ↓
Productionalize agent — converts approved design into real production code
   transfers design intent, not code; re-derives against the real source
        ↓
Production validator
        ↓
Redesigned codebase, kept in sync on every merge to the platform's main
   sync lands on UAT, never straight to prod
        ↓
End user has a fully custom app
```

### Why the mirror is visual-only, and why that matters

The mirror is **mockware**. It has no features, no business logic, no API calls, no state management. It exists to be looked at and edited.

This single property answers the strongest objection raised in the session. If the mirror were a *functional* mirror, the [[Concepts/Product/Mechanisms/No_New_Requests_Invariant|arrangement-only invariant]] would have to survive a translation in both directions, and the customer's ability to verify it by diffing a branch — the thing that makes the invariant saleable rather than merely claimed — would be lost. Because the mirror is visual only, **the invariant never crosses the translation boundary.** It lives entirely in the productionalize step, on real production code, where it remains a diff the platform's own engineers can read.

### Three reasons the mirror earns its cost

1. **Model fluency.** Models are materially better at JSX than at Flutter widget trees or Kotlin layouts. Freedom is the point, per the enum finding, and freedom is worth most in the representation the agent handles best.
2. **A screenshot oracle where the pivot said there was none.** The 2026-07-27 pivot named the absence of a layout accept condition as the remaining engineering risk. A browser renders and screenshots trivially; a VLM can judge the result. This is not deterministic the way WCAG is, but it is an oracle where there was none, and it only exists cheaply in a browser. **This is an architectural justification for the mirror that has nothing to do with preview.**
3. **The end user watches it happen.** Founder: *"if we really want the end user doing this they need to be able to visually see it just like in any other online builder, if anything it's an anti-pattern not to."* Correct. Live generation is table stakes in this category now.

### The cost structure, which is the opposite of how it first appears

The partner's initial read treated mirror regeneration as the recurring cost driver. That was backwards.

| Operation | Frequency | Scope |
|---|---|---|
| Mirror regeneration | Once per release (weekly to monthly) | Per **platform**, amortized across every tenant |
| Design iteration | Many per week | Per **tenant** — the high-frequency operation |
| Productionalize | Once per accepted design, plus re-application on sync | Per **tenant** |

Founder: *"this is likely one big token push at the beginning to make all the more frequent transactions cheaper (just visual, and where the iteration actually happens)."*

That is the correct shape: pay once, at low frequency, amortized widely, to make the high-frequency operation cheap. The mirror is the **low-risk, well-argued** part of this design.

## Where the risk actually sits: productionalize

Both parties converged here. Founder: *"absolutely the productionalize part is what actually makes the product the product and what makes this ambitious, exactly how I like it."*

It is also the step where every difficulty initially misattributed to the mirror actually lives:

- It is the only step that must preserve the [[Concepts/Product/Mechanisms/No_New_Requests_Invariant|arrangement-only invariant]].
- It is the translation that actually matters, because its output ships.
- It has no cheap oracle — screenshots validate the mock trivially, but validating production requires building and running the real app.

### The specific hazard: the mock has no edge cases

The mock's featurelessness is exactly what makes it cheap **and** exactly what makes productionalize hard.

A featureless mock does not know that a list is paginated, that a name can be 47 characters, that a screen has loading, empty, error and overflow states. The design agent will therefore produce layouts that are correct against *ideal* data. The productionalize agent then has to reconcile a design authored in a world with no edge cases against production code that is mostly edge cases.

**Two cheap mitigations, both proposed in session:**

1. **Mock every state, not just the happy path.** Mocking is the mirror's job — tokenization only tokenizes assets. If the mirror generates each screen's states — empty, loading, error, long-string, overflow — rather than one ideal render, the mock carries realistic variance, the design agent designs against it, and productionalize stops being a reconciliation problem. Small addition to a step already being built; removes most of the downstream difficulty.
2. **Screenshot-validate the production side too.** Flutter Web is canvas-painted and pixel-identical to mobile (2026-05-25). The production validator can build to web and diff screenshots against the approved mock. Same oracle on both sides, and the mirror's fidelity requirement becomes *measured* rather than assumed.

### We never touch their trunk

This arrived late in the session, as a consequence the founder noticed rather than a goal he set out with: *"now the integration is actually a lot easier, we never touch their main codebase out of the tokenization."*

Pushed on, it got stronger. Not one PR at tokenization and then never again — **no PR at all**. Recompose maintains a **shared tokenized fork** of the platform's app as its own base, kept current against their main by an agent; each tenant's design is a further fork of that base. Founder: *"we actually just have a shared fork which is our base which is a tokenized version, and they can do whatever they want and the agent essentially just figures everything out without approval (steerable of course if THEY WANT to be involved, but never actually touches their codebase)."*

**What this kills.** The largest named adoption blocker in the vault — the Codex cold read's *"internal resistance to letting an external system drive production UI"* — is gone rather than mitigated. The reason is organizational more than technical: an external agent with **write** access to the trunk needs engineering leadership sign-off; **read** access does not. It changes who has to say yes, which matters more for a solo founder than the engineering saving does.

It also gives a better trust primitive than review. A PR is a one-time gate that costs the platform attention. A fork is **continuously and self-serve auditable** — they can diff it against their main whenever they like, without involving us.

**What it does not kill.** The QA and release objection. They still ship a binary built from code an agent wrote. Functional equivalence still carries that weight and is still unbuilt.

**What it costs.** The maintenance burden moves to Recompose permanently. Their own devs are not maintaining tokens inside code they understand; our agent re-reconciles an external fork against every structural change they make, forever. Two sync layers result. Founder, on re-tokenization: *"I don't want to say never again, it will happen again if they expand visually or add new screens, but this won't happen often."* Under the shared-fork model that recurrence is entirely on our side of the line.

**What it decided by implication.** The **layout enum** — the option the founder rated highest on 2026-07-27 — is dead, because it requires writing generated layouts into the customer's trunk. Founder, confirming: *"yes this is dead... just touching and maintaining their production code sounds like a mess. Agentic separate forks you essentially don't have to think about unless there is an error is better."*

**The question it creates.** If the source of truth for a tenant's design is a Recompose fork, the branded binary builds from our fork, so something connects it back to their release train. *"We never touch your source"* is true; *"we're not in your pipeline"* is not. The founder rates this the easy part — *"the real problem is getting them to trust it"* — which is probably right, and is also why it should have a prepared answer rather than being discovered on a call.

### Sync lands on UAT, not prod

Founder: *"sync will probably have to be on UAT not prod, we can't just do everything at launch, we do it at UAT and surface anything that may need a fix."*

This is a load-bearing decision, not an implementation detail. It **converts a product-quality problem into a throughput problem.** A 1% catastrophic rate landing on main is unsellable and no platform would accept it. The same 1% landing in UAT is a queue a human works. This is what makes the error budget below acceptable rather than disqualifying.

## The positioning that falls out of it

Founder: *"I don't think we should be promising that agents are magic. We're just promising that one person can manage a hundred at a time."*

This is the strongest positioning line the project has produced. It is honest, it is the opposite of the category's default claim, and it matches the forward-deployed year-one model exactly. Most usefully, it turns the error budget from an embarrassment into a **design spec**: a human in the loop is the stated architecture, not a fallback for when the agents fail.

**Stated error budget:** ~95% clean, ~4% minor error, ~1% significant failure — acceptable *given UAT*.

**The metric that makes the claim real:** interventions per hundred tenants per month. That ratio is the entire "one person manages a hundred" claim, it is the thing that decides whether the forward-deployed model has a ceiling, and it cannot be asserted before it is measured. Instrument it from the first customer.

## Premises

**Locked this session:**

- P16 — Structural presets and enum classification cannot produce genuine differentiation; they are bounded by the platform's original design language. *Tested, not reasoned.*
- P17 — The design agent operates with full freedom over layout, constrained only by the arrangement-only invariant.
- P18 — The JSX mirror is **visual only** — mockware, no features. The invariant is enforced at productionalize, on production code, where it stays customer-verifiable.
- P19 — Design validation is screenshot-based. This is the answer to the layout accept-condition problem named in the 2026-07-27 pivot.
- P20 — Sync lands on UAT, never directly on prod.
- P21 — Positioning is human leverage, not agent autonomy. One person manages a hundred.
- P22 — Tokenization is forward-deployed for the MVP. The founder does it and confirms it is right.
- P23 — **Recompose never writes to the platform's trunk.** A shared tokenized fork is the base; each tenant's design is a fork of it; both are agent-maintained. The platform grants read access, and that is the integration. Supersedes P13a.
- P24 — The layout enum is dead. It is incompatible with P23.

**To test:**

- T13 — Can the productionalize agent hit ~95% clean on a real, non-trivial screen?
- T14 — Does a VLM screenshot judgement correlate with human design judgement well enough to terminate the validator loop?
- T15 — What is the true interventions-per-hundred-tenants-per-month ratio?
- T16 — Does mirror generation hold up on a codebase the founder did not write? Everything so far is CombatDen.
- T17 — How does the branded build reach the platform's release train, given the design's source of truth is a Recompose fork? Rated the easy part; currently unanswered.
- T18 — Does the agent-maintained tokenized fork survive real upstream churn, or does drift compound once no human who understands a change is in the loop? This is the cost of P23 and it only shows up over months.

## Approaches considered

**A — The architecture above.** Whole-codebase JSX visual mirror, free design agent, screenshot validation, productionalize, UAT sync. **Chosen.**

**B — No mirror; design agent edits real source, preview via the real app compiled to web.** This was the 2026-05-25 conclusion and it is correct *for a token-only product*. Rejected for three reasons that only became true after the layout pivot: no cheap screenshot oracle, worse model fluency in Flutter, and no fluid real-time visual feedback for the end user. Founder: *"the end user can't see anything happen."*

**C — Per-screen ephemeral mirroring.** Proposed by the partner and **withdrawn in session as poorly reasoned.** It was premised on the mirror being expensive to maintain. Once the mirror is understood as cheap visual mockware regenerated once per release, per-screen scoping buys nothing and costs cross-screen [[Concepts/Product/Mechanisms/Modal_Coherence|coherence]].

## Open questions

1. **95/4/1 of what unit?** Per screen, per tenant-redesign, or per sync operation? These differ by orders of magnitude in human workload and the answer determines whether the error budget is comfortable or brutal.
2. **What terminates the design validator loop?** Screenshot judgement gives an oracle but not a stopping condition. Unbounded loops are unbounded cost.
3. **Live-testing tooling for the production validator.** Founder raised Codex as strong at live testing, or subscribing to a startup that specializes in it. Candidate, not a decision.
4. **Does mirror generation generalize off-CombatDen?** Untested against any app the founder did not write.
5. **Pricing.** Explicitly deferred. Founder: *"for the price it's still unknown, this is really not that important yet."* The submitted YC application carries $100/month per branded tenant as a working figure; a $200 figure was floated in session; neither is decided. Note the per-tenant versus per-platform distinction matters enormously once it is decided, because sync cost multiplies by tenant count.
6. **Human oversight at scale.** Founder: *"long term the company might need to hire an engineer to watch over all of these agents at a really big scale, but that's not for us to worry about at this exact moment."* Correctly deferred; recorded because it is the first named limit on the leverage claim.

## The assignment

**Not a build task.** The architecture is now specified well enough that the binding constraint is once again commercial.

1. **Instrument nothing yet — measure one thing.** Run the productionalize step by hand on one real CombatDen screen: take a redesigned mock, produce the production Flutter, and count what broke. That single number is T13, it is the load-bearing unknown in the whole design, and it takes an afternoon.
2. **The unexecuted assignment still stands.** Produce ten named white-label platforms with real tenant volume and a named human at each, starting with platforms that already run a design service. No platform has seen any of this. The architecture is now three sessions deep and zero conversations deep.

## What I noticed about how you think

- **You tested instead of reasoning, and it changed your mind.** *"I just tested preset enums for structure and I realized it's always going to be bounded by the design language originally."* Eight months of this project have been reasoning. This is the first finding that came from a build, and it immediately overturned an approach you had already partly implemented. That is the most valuable thing in the session and it should be the pattern, not the exception.
- **You corrected the partner's framing precisely rather than defending your design generally.** *"I need to be clear the JSX has no features, it just demoware fully mockups no production stuff so it's not a production mirror, it's a visual mirror."* That one distinction dissolved the strongest objection on the table. You did not argue the objection was unimportant; you identified the exact premise it rested on and removed it.
- **You got the cost frequency right when the partner got it backwards.** You separated the once-per-release operation from the many-per-week operation and saw that the expensive infrequent one buys cheapness in the frequent one. That is a cost-structure instinct you have shown before, in the 2026-05-01 pricing session and the 2026-05-25 Appetize analysis.
- **You reached for the honest claim over the impressive one.** *"I don't think we should be promising that agents are magic, we're just promising that one person can manage a hundred at a time."* Founders usually inflate here. You deflated, and the deflated version is both more defensible and more differentiated than the inflated one would have been.
- **You still name the future problem and then set it down.** The engineer-watching-agents-at-scale point, the Codex tooling point, the pricing point — all raised, all correctly deferred. You have gotten noticeably better at this. The risk is the mirror image: the June 2 validation assignment has now been deferred for eight weeks, and deferral is only a strength when the thing deferred is genuinely not yet binding.
